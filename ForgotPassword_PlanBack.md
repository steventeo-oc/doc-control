# Forgot Password — Plan-Back (email-based self-service reset)

Companion to `CLAUDE.md`. Drafted 2026-09-15 at the owner's request, found
as a real gap during the design-redesign UI/UX pass: there is currently
**no way for a locked-out user to recover their own account**. Self-service
`POST /users/{id}/password` requires the *current* password; the only
recovery path today is an admin resetting it for them (`UserService.
changePassword`, `!selfService && isAdmin`). This plan adds a standard
email-link reset flow, reusing the Microsoft Graph sender that already
exists (Phase 2b) rather than building any new email infrastructure.

Grounded directly in the current code before writing this (no guessing):
`NotificationSender.send(User, subject, body)` is the entire outbound
boundary (Graph in prod, log-only in dev, selected by
`doccontrol.notification.enabled` — nothing about this feature needs to
touch that selection); `SystemActor` + `AuditService.recordAs(actor, …)`
is the existing mechanism for audit rows written outside any security
context (the daily sweep already does exactly this); `SecurityConfig`
already has the `permitAll()` precedent for `POST /auth/login`; the SPA's
`authApi`/`api.post` client and CSRF flow need no changes — a fresh page
load already seeds the XSRF-TOKEN cookie via `AuthContext`'s `/auth/me`
call before any POST fires, the same way the existing Login page relies on
it today.

## 1. Flow

1. User clicks "Forgot password?" on the login page → `/forgot-password`.
2. Enters their email, submits. Backend **always** responds the same way
   (202, generic message) whether or not that email exists — see §3.
3. If the email matches an active user, a single-use token is generated,
   stored (hashed) with an expiry, and emailed via the existing
   `NotificationSender` with a link to `/reset-password?token=<raw>`.
4. User clicks the link, lands on `/reset-password`, enters a new password
   (+ confirmation field — see §5), submits.
5. Backend validates the token (exists, unexpired, unused), sets the new
   password, marks the token used, writes the existing `password_changed`
   audit action with a new `via: "email_reset"` detail, and any other
   outstanding tokens for that user are left alone (already superseded at
   issuance time, see §3).

## 2. Schema — migration V10

```sql
CREATE TABLE password_reset_token (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES "user" (id) ON DELETE CASCADE,
    token_hash VARCHAR(64) NOT NULL UNIQUE,
    expires_at TIMESTAMP NOT NULL,
    used_at TIMESTAMP,
    created_at TIMESTAMP NOT NULL DEFAULT now()
);

CREATE INDEX idx_password_reset_token_user ON password_reset_token (user_id);
```

`token_hash` is SHA-256 hex of the raw token — **the raw token is never
stored**, only ever exists in memory long enough to email it and return
202. A DB dump (or a careless log line) yields nothing usable. Cascade
delete on the user FK — no orphaned tokens possible.

## 3. Security decisions (mine to resolve, stated explicitly, not left to
   whoever implements this)

- **No account enumeration.** `POST /auth/forgot-password` returns the
  identical 202 + generic body ("If that email is registered, we've sent a
  reset link.") whether the email exists, doesn't exist, or belongs to an
  inactive user. The difference must never be observable from the
  response, timing aside (best-effort — not attempting constant-time
  padding, this isn't a login endpoint).
- **Token entropy & storage**: 32 bytes from `SecureRandom`, base64url
  encoded for the emailed link; only its SHA-256 hash is persisted.
  Lookup on reset hashes the incoming token and queries by `token_hash`.
- **Expiry**: configurable, default **30 minutes** — short because this is
  a bearer credential sent over email, a channel we don't control end to
  end.
- **Single-use**: `used_at` set on successful reset; a used or expired
  token fails the same generic way as a bogus one (see §6 — the reset
  endpoint doesn't distinguish "expired" from "invalid" in its response).
- **Supersede on reissue**: requesting a new reset token deletes any
  existing unused tokens for that user first — at most one live token per
  user at a time (mirrors the existing "a newer outcome retires the older
  one" pattern already used for pending-effective version approvals).
- **Resend cooldown**: if an unexpired token for the user was already
  created within the last **2 minutes** (configurable), silently skip
  sending another — still return the identical 202. Cheap mail-bombing
  guard with no new infrastructure; not a full rate-limiter, and I'm not
  proposing a CAPTCHA for an internal compliance tool (flagged as a
  "Later" hardening item if this is ever exposed beyond the company
  network, not built now).
- **Audit trail, two entries** (both via the existing `AuditService`):
  - On issuance (only when the email matched a real user — nothing to
    attach an audit row to otherwise): `entity_type="user"`,
    `action="password_reset_requested"`, actor = `SystemActor.get()`
    (there is no authenticated caller — same precedent as sweep-driven
    audit rows).
  - On successful reset: the **existing** `action="password_changed"`
    (not a new action string — this keeps it inside the Activity feed's
    current rendering with zero frontend risk), `details={"self_service":
    false, "via": "email_reset"}`, actor = the target user themselves
    (consistent with how a self-service change records the user as actor
    of their own row, even though no session exists at reset time — the
    action is unambiguously theirs).

## 4. New config

`AppProperties` (new, `@ConfigurationProperties(prefix = "app")`, sibling
to the existing `CorsProperties` which already binds `app.cors.*`):

```yaml
app:
  base-url: http://localhost:3000   # DOCCONTROL overrides use APP_BASE_URL
  cors:
    allowed-origins: http://localhost:3000
```

`PasswordResetProperties` (new, `@ConfigurationProperties(prefix =
"doccontrol.password-reset")`, following the existing
`ReviewProperties`/`AcknowledgmentProperties` shape):

```yaml
doccontrol:
  password-reset:
    expiry-minutes: 30
    resend-cooldown-minutes: 2
```

Both env-overridable per this project's usual convention
(`APP_BASE_URL`, `DOCCONTROL_PASSWORD_RESET_EXPIRY_MINUTES`,
`DOCCONTROL_PASSWORD_RESET_RESEND_COOLDOWN_MINUTES`).

## 5. Endpoints (both added to `AuthController`, both `permitAll()` in
   `SecurityConfig` — the entire point is they work while logged out)

- `POST /auth/forgot-password` — body `{email}` → always `202 Accepted`,
  generic message. Never throws for "not found."
- `POST /auth/reset-password` — body `{token, newPassword}` → `204` on
  success; `400` with one generic message ("This reset link is invalid or
  has expired.") for every failure case (missing/expired/used token) —
  deliberately not distinguishing them in the response, same
  non-enumeration spirit as §3.

## 6. Email content

Plain text (matches `GraphNotificationSender`'s `contentType: "Text"`,
same as every other notification today):

```
Subject: Reset your Document Control password

Someone requested a password reset for this account. If this was you,
click the link below within 30 minutes to choose a new password:

{app.base-url}/reset-password?token={raw token}

If you didn't request this, you can ignore this email — your password
hasn't changed.
```

## 7. Frontend

Two new pages, built in the **already-migrated Phase 1 design system**
(`Card`/`Input`/`Label`/`Button` — not the old CSS; these live right next
to `LoginPage.tsx` which is already reskinned, so building them in the old
style would be immediately inconsistent):

- `ForgotPasswordPage.tsx` (`/forgot-password`): email field, submit →
  the generic confirmation message (never a different message for
  "found"/"not found" — the frontend must not undermine the backend's
  non-enumeration guarantee by, say, checking existence some other way).
- `ResetPasswordPage.tsx` (`/reset-password`, reads `?token=` from the
  URL): new password + confirm-new-password fields (client-side match
  check before submit — unlike the existing change-password Dialog, there
  is no "current password" field here to serve as an identity check, so a
  confirmation field is the right guard here, not scope creep), submit →
  success message + link to `/login`, or the server's generic error +
  a link back to `/forgot-password` to request a new one.
- `LoginPage.tsx`: add a "Forgot password?" link beneath the form.
- `App.tsx`: two new public routes (not behind the auth guard).
- `activitySummary.ts`: extend the existing `user/password_changed` case
  to say "via email reset" when `details.via === 'email_reset'` — small,
  additive, improves the audit trail's readability (this is an ISO 9001
  tool; "was this self-service, admin, or an email reset" is exactly the
  kind of distinction this project already makes for the daily sweep's
  `triggered_by`).

## 8. Testing

New `PasswordResetTests.java` (backend), covering: token issuance on a
real email, non-enumeration (same response for a nonexistent email),
resend-cooldown (second request within the window sends nothing new),
expiry (an expired token is rejected), single-use (a used token can't be
replayed), reissuance supersedes the prior token, and a successful reset
writes the `password_changed` audit row with `via: "email_reset"`.

## 10. Out of scope

CAPTCHA/bot mitigation beyond the resend cooldown (flagged as a possible
"Later" item, not built now); SMS or any non-email channel; "security
questions" or any secondary verification; changing the existing
self-service change-password Dialog or the admin-reset endpoint — both
stay exactly as they are, this is a third, independent path.
